# FFI 绑定工具 Spike — cxx vs 手写 C ABI（M0 Step 0，D28 决策闸门）

> 状态：✅ 已执行完毕，D14 冻结为 **手写 C ABI（方案 A）**，见设计文档 §8.1。
> 关联：设计文档 v0.6 §8.1 / TDD 计划 M0 Step 0 / 评审问题 1（P0）。

## 被测对象

两种方案各实现最小内核（目标各 ~200 行），覆盖 3 个代表函数：

| 函数 | 覆盖的难点 |
| :--- | :--- |
| `lt_session_create` | libtorrent session 生命周期、`boost::asio` 启动、异常边界（构造失败） |
| `lt_pop_alerts` | alert 队列跨边界传递、**扁平化 + 生命周期/所有权**（libtorrent alert 由 session 持有，下次 pop 失效） |
| `lt_status` | `torrent_status` 快照拷贝（字段对齐、值语义） |

## 对比维度矩阵

| 维度 | 方案 A：手写 C ABI + bindgen | 方案 B：cxx | 判据（数据填这里） |
| :--- | :--- | :--- | :--- |
| 构建复杂度 | 手写 `lt.h` + CMake 静态库 + build.rs 链接 | cxx bridge 代码生成 + CMake 集成 | 编译时长 / 依赖数 |
| 代码行数 | `lt_kernel.cpp` + Rust glue | `bridge.rs` + C++ impl | 行数比 A/B |
| 内存契约维护 | 手动：Rust 预分配缓冲 + C++ 填 + capacity 协议 | `UniquePtr`/`SharedPtr` 自动管理；alert 仍要手动扁平化 | 契约代码占比 |
| 异常/回调处理 | 手动 try-catch 包每个导出函数 | cxx 内置异常边界 | 边界代码行数 |
| alert 扁平化工作量 | C++ 侧 case + 值结构体 + 拷贝进 Rust 缓冲（本就要做） | 同上（cxx 不解决 alert 扁平化本身） | 是否重复劳动 |
| 调试难度 | gdb/lldb 常规；跨语言栈较难 | 同上 | — |
| 长期维护（alert 增删字段） | 改 `lt.h` + cpp + Rust 侧（bindgen 重跑） | 改 bridge + 两侧 | 单次改动涉及文件数 |
| 许可证/依赖风险 | 零额外依赖 | cxx crate 依赖（MIT/Apache） | — |

## 验收判据（预注册，避免 spike 后纠结）

1. **若满足以下全部 → 选 cxx（方案 B）**：
   - 行数比 A/B ≥ 1.5（手写方案明显更啰嗦）
   - cxx 版本编译通过（含 Windows MSVC）
   - `lt_pop_alerts` 的 alert 队列在 cxx 下可正确跨边界（生命周期可用 `SharedPtr` 表达）
2. **若出现以下任一 → 选手写 C ABI（方案 A）**：
   - cxx 遇到 libtorrent 特有坑：`std::shared_ptr<torrent_status>`/回调对象跨 FFI 边界生命周期难以表达、需要大量 `#[cxx::bridge]` 手写类型映射、异常语义与 libtorrent 冲突
   - 行数比 A/B < 1.5（两者代码量相当，则选更少依赖/更可控的手写 C ABI）
   - 构建集成复杂度不成比例（cxx 与 CMake/vcpkg 的 libtorrent 静态库链接出问题）
3. **默认倾向**（无显著差异时）：手写 C ABI + bindgen——契约定死可复用于其他语言/工具，无 codegen 构建依赖。

## 附带验证项（评审提醒，M0.3 同批）

**做种停止路径**：`torrent_finished → lt_pause` 在 libtorrent 2.0.x 的可靠性。
- 30 行小测试：本地 seeder 做种 2MB → 客户端跑到完成 → 记录 alert 序列
- 断言：`torrent_finished`（或等价 state_changed finished）**先于**我们主动 pause 产生的 `torrent_paused`
- 结论写回设计文档 §10.1（若 2.0.x 上不可靠 → 回退方案：完成时 `lt_remove(delete_data=false)` 或 session 级 seed_ratio 复核）

## 结论填写区（spike 完成后填）

### 实测数据（2026-08-16，Windows x64，MSVC 2022 BuildTools，libtorrent 2.1.1 vcpkg ABI-100）

**体积对比（同一最小内核：session / add_magnet / status / pop_alerts）**

| 方案 | 契约 | 实现 | 合计 |
| :--- | :--- | :--- | :--- |
| A 手写 C ABI | `ffi/lt.h` 71 行 | `ffi/src/lt_kernel.cpp` 249 行 | **320** |
| B cxx | `spike/cxx/src/lib.rs` bridge 43 行 | `spike_impl.hpp` 53 + `spike_impl.cpp` 122 | **218** |

- 行数比 A/B（公平口径，contract 双方都计入）= **320 / 218 = 1.47**，未达 ≥1.5。

**构建与集成**：A 一次通过（cmake + vcpkg target 全自动链接）；B 编译通过但需 5 轮修复——
cxxbridge 不支持 `&CStr`/tuple 返回、`&self` 要求 C++ const 方法、共享 struct 需 `CXXBRIDGE1_STRUCT_*`
守卫宏由 C++ 侧定义、生成头路径为 `cxxbridge/include/<crate>/src/lib.rs.h`、以及 vcpkg boost 1.91
header-only asio 导致非模板 `boost::throw_exception` 未解析（需 spike-only shim）。→ 构建集成复杂度不成比例。

**alert 跨边界**：两方案都需 C++ 侧手写扁平化（case + 值结构体 + 拷贝出队列）；B 的 `rust::Vec<Alert>`
可表达队列，但生命周期仍靠拷贝（不依赖 SharedPtr），无显著优势。

**libtorrent 特有坑**：命中（boost shim + asio 编译模式差异）。

### 结论表

| 项 | 结果 |
| :--- | :--- |
| 编译时长 A / B | A: 已有 cmake 产物（增量）；B: cargo 冷构建 ~28s + 5 轮集成修复 |
| 行数 A / B（cpp/glue 合计） | 320 / 218 = 1.47（< 1.5） |
| alert 跨边界是否 cxx 可表达 | 可（拷贝语义），但无优势（扁平化仍手写） |
| 是否遇到 libtorrent 特有坑 | 是（boost throw_exception shim） |
| 做种停止路径验证 | ✅ 2026-08-17 已执行：`m0_finished_pause.rs` 实测通过（fin<paused 顺序恒定；ABI100 status() 不反映暂停，同步点=torrent_paused alert；结论在 §10.1） |
| **D14 冻结结论** | ☑️ **手写 C ABI（方案 A）** ☐ cxx |
| spike 执行日期 | 2026-08-16 |

**冻结理由**（对齐预注册判据）：
1. 行数比 1.47 < 1.5 → 判据 1 不满足；
2. 判据 2 命中：构建集成复杂度不成比例（5 轮 cxx 特有修复 vs A 零修复）+ libtorrent/boost 特有坑（shim）；
3. 默认倾向成立：手写 C ABI 契约定死（lt.h 复用其他语言/工具），无 cxx codegen 构建依赖。
4. 附带验证（做种停止 `torrent_finished → lt_pause`）已随 M0 e2e 同批执行并写回设计 §10.1（`torrent_finished`/`torrent_paused` 顺序恒定；STATE 桶 flattener 用 `a->type()` 区分，dynamic_cast 在 vcpkg libtorrent 构建上实测失效）。
